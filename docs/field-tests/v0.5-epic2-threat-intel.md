## Controlled Two-Generation Workflow

When a controlled feed needs to move from generation A to generation B, use a
source edit rather than deleting/recreating the source or editing SQLite:

```bash
sudo pihole-ai intel source update controlled-field-test \
  --url https://raw.githubusercontent.com/Carbonarakarlsson/pihole-ai/945d20e5400ba5a02d3ec5096a3b691646103865/docs/field-tests/fixtures/controlled-threat-feed.txt
sudo pihole-ai intel update --source controlled-field-test
sudo pihole-ai intel rollback --source controlled-field-test
sudo pihole-ai intel update --source controlled-field-test
```

The source update must preserve the active generation and prior generations
until the explicit update command runs. The URL edit clears HTTP validators so
the commit-pinned fixture is fetched. Commit-pinned raw URLs are preferred for
deterministic field tests because branch-based raw URLs may be cached upstream.
The final update should reactivate the already-stored generation B with
`changed=True` and `reused_generation=True`, not create duplicate generations or
entries. If the server returns HTTP 304, the expected result is still
`changed=True`, `not_modified=True`, `reused_generation=True`, and
`active=<generation B>` because validators describe the remote representation,
not necessarily the classifier-active generation after rollback.

## Defects Fixed During Repository Pass

### Field Defect: updater lock path used `/tmp`

- Expected: updater lock should use a PiHole-AI-managed runtime path accessible
  to the service identity.
- Actual: the lock defaulted to `/tmp/pihole-ai-intel-update.lock`.
- Severity: medium; this weakens appliance isolation and complicates
  service-user validation.
- Fix: default lock path moved to `/run/pihole-ai/intel-update.lock`, with
  `PIHOLE_AI_INTEL_LOCK_PATH` as a test/operator override.
- Regression: `tests.test_intel.ThreatIntelTests.test_update_lock_uses_exclusive_file_lock`.

### Field Defect: updater timer lacked jitter and explicit start timeout

- Expected: timer has conservative scheduling with randomized delay, and the
  oneshot updater has bounded execution.
- Actual: timer had `Persistent=true` but no randomized delay; service had no
  explicit `TimeoutStartSec`.
- Severity: medium; repeated appliance updates could synchronize and hung
  updates would be less obvious.
- Fix: generated services include `TimeoutStartSec=300`; generated timer
  includes `RandomizedDelaySec=15min`.
- Regression: `tests.test_service.ServiceTests.test_generate_intel_update_timer_file`.

### Field Defect: installer did not enable updater timer

- Expected: lifecycle enable/disable includes the updater timer, while runtime
  start/stop remains scoped to the three daemons.
- Actual: install/enable only enabled collector, engine, and dashboard.
- Severity: medium; automatic feed management would not run after boot.
- Fix: added `ENABLE_UNIT_NAMES` containing the three daemons plus
  `pihole-ai-intel-update.timer`.
- Regression: service and appliance lifecycle dispatch tests now assert
  `ENABLE_UNIT_NAMES`.

### Field Defect: enabled timer could update feeds despite auto-update default

- Expected: unattended timer execution honors
  `PIHOLE_AI_INTEL_AUTO_UPDATE_ENABLED=false` by default.
- Actual: the timer command would update enabled sources whenever triggered.
- Severity: medium; configured sources could update unattended before the
  operator opts in to automatic updates.
- Fix: non-interactive all-source updates return a safe skipped result while
  auto-update is disabled. Manual `pihole-ai intel update` remains available.
- Regression:
  `tests.test_intel.ThreatIntelTests.test_automatic_update_respects_auto_update_setting`.

### Field Defect: source URL changes required delete/recreate or SQLite edits

- Expected: operators can edit a managed source URL through supported CLI while
  preserving active/prior generations for rollback testing.
- Actual: source add/remove/show/enable/disable existed, but no safe partial
  source edit command existed. Removing the source could delete generation
  history.
- Severity: high for controlled Epic 2 validation; it blocked deterministic
  generation A -> B -> A testing without direct database modification.
- Fix: added `pihole-ai intel source update SOURCE_ID [options]` with partial
  updates, URL/fetch-setting validator reset, generation preservation, and
  clear JSON/text output.
- Regression:
  `tests.test_db.DatabaseTests.test_source_update_preserves_generations_and_clears_validators_for_url_change`
  and `tests.test_cli.CLITests.test_intel_source_update_dispatches_partial_changes`.

### Field Defect: update after rollback did not reactivate matching generation

- Expected: A -> B -> rollback A -> update B reactivates the existing stored B
  generation, reports `changed=True` and `reused_generation=True`, and leaves
  exactly one active generation.
- Actual: the updater treated a downloaded hash that existed in historical
  generations as unchanged, even when the matching generation was inactive and
  the active generation was different.
- Severity: high for controlled Epic 2 validation; it broke deterministic
  rollback/reactivation testing and could leave classifier-visible indicators on
  the wrong generation.
- Fix: update outcomes are now relative to the active generation. Matching
  active content is unchanged; matching inactive valid same-source content is
  atomically reactivated; new content creates a new generation.
- Regression:
  `tests.test_db.DatabaseTests.test_update_reactivates_inactive_generation_with_matching_content`
  and `tests.test_db.DatabaseTests.test_repeated_ab_update_rollback_cycle_does_not_duplicate_generations`.

### Field Defect: HTTP 304 after rollback did not reactivate remote generation

- Expected: after B active -> rollback A, a 304 response for unchanged remote B
  reactivates existing generation B with `changed=True`, `not_modified=True`,
  and `reused_generation=True`.
- Actual: the 304 path treated the currently active generation A as unchanged
  because validators were assumed to describe local classifier activation.
- Severity: high for Raspberry Pi acceptance; immutable fixture URLs can return
  304 while the local active generation intentionally differs after rollback.
- Fix: source state now stores `remote_generation_id` alongside validators and
  content hash. Rollback preserves remote state, and 304 updates reactivate the
  remote generation when it differs from `active_generation`.
- Regression:
  `tests.test_db.DatabaseTests.test_http_304_reactivates_remote_generation_after_rollback`.

### Field Defect: migration 8 backfilled remote generation from active state

- Expected: when migration runs after rollback, `active_generation=A` and
  `remote_generation_id=B` if the latest successful HTTP 200 fetch activated B.
- Actual: migration 8 could set `remote_generation_id=A` because A was active
  during migration, causing the next 304 to report unchanged with two A entries.
- Severity: high for upgraded Raspberry Pi appliances that already completed
  rollback before installing the 304 fix.
- Fix: migration 9 repairs missing or suspect remote identities from latest
  successful HTTP 200 audit history, and runtime 304 resolution can recover from
  bad explicit references using the same audit evidence.
- Regression:
  `tests.test_migrations.MigrationTests.test_migration_9_repairs_remote_generation_from_latest_http_200_audit`
  and
  `tests.test_db.DatabaseTests.test_http_304_reactivation_can_recover_bad_remote_reference_from_audit`.

## Release Recommendation

Epic 2 threat-intelligence generation lifecycle: accepted.

The strongest acceptance condition was proven:

> A failed, empty, malformed, oversized, or suspicious feed update must never
> replace the currently active valid generation.

The second critical condition was proven:

> Every threat-intelligence evidence item used in a decision must identify the
> exact active source generation and freshness state that produced it.

Remaining non-blocking debt:

- source metadata edit auditing remains limited
- generation/audit retention policy needs refinement
- broader feed-format validation is still needed beyond the controlled fixture
