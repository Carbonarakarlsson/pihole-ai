## Defects Found And Fixed

### Release blocker: units selected non-importable system Python

Severity: release blocker.

Reproduction:

1. Run appliance install planning from an environment where PiHole-AI is installed outside system Python.
2. Inspect generated unit commands.
3. Validate `/usr/bin/python3.13 -m pihole_ai.cli --version` under the intended service context.

Expected:

- Units and launcher use the same stable environment where the wheel-installed package is importable.
- Installer fails preflight before mutation when no valid interpreter exists.

Actual before fix:

- Generated units used `/usr/bin/python3.13 -m pihole_ai.cli ...`.
- System Python could not import `pihole_ai`, producing `ModuleNotFoundError`.

Fix:

- Added structured executable discovery/validation.
- Validation runs `<candidate-python> -c "import pihole_ai, pihole_ai.cli"` and `<candidate-python> -m pihole_ai.cli --version`.
- Preflight blocks install with `install.executable.package_not_importable` when no valid stable target exists.
- Source-checkout `.venv` paths are rejected in appliance mode unless explicit development mode is enabled.
- Supported wheel path is now:

```bash
sudo python3 -m venv /opt/pihole-ai/venv
sudo /opt/pihole-ai/venv/bin/pip install dist/pihole_ai-0.4.0rc1-py3-none-any.whl
sudo /opt/pihole-ai/venv/bin/pihole-ai install
```

Regression tests:

- `test_system_python_without_package_is_rejected`
- `test_system_python_with_importable_package_is_accepted`
- `test_dedicated_appliance_venv_is_accepted_when_importable`
- `test_project_venv_rejected_for_appliance_mode`
- `test_project_venv_allowed_only_in_development_mode`
- `test_console_script_with_invalid_interpreter_is_rejected`
- `test_preflight_blocks_non_importable_python_before_mutation`
- `test_dry_run_reports_executable_block_without_mutation`
- `test_generated_units_and_launcher_use_validated_target`
- `test_install_status_reports_executable_validation`
- `test_systemd_diagnostic_reports_executable_validation`

### Blocker: wheel install plan leaked source checkout paths

Severity: release blocker.

Reproduction:

1. Install the rc1 wheel into a fresh venv outside the checkout.
2. Run `pihole-ai install --dry-run --no-start` from the wheel-installed CLI.
3. Inspect generated unit and launcher paths.

Expected:

- Unit `WorkingDirectory` is a stable appliance runtime path.
- Launcher points to the installed CLI executable.
- No source checkout or `.venv` references appear.

Actual before fix:

- `WorkingDirectory` pointed at the source checkout.
- Existing launcher preservation path pointed at the source checkout `.venv`.

Fix:

- Default install plan working directory now uses `/var/lib/pihole-ai`.
- Generated launcher now points at the installed `pihole-ai` executable beside the active Python executable.
- Legacy launcher removal remains backward compatible for older project `.venv` launchers.

Regression tests:

- `test_install_plan_defaults_to_runtime_working_directory`
- `test_launcher_content_can_point_to_installed_cli_executable`
- `test_service_install_dry_run_uses_runtime_directory_for_wheel_install`

### Major: `pihole-ai doctor` traceback under unhealthy config/database conditions

Severity: major.

Reproduction:

1. Run `pihole-ai doctor` on the field host with current unhealthy/incompatible appliance state.

Expected:

- Clean diagnostic output with no traceback.

Actual before fix:

- `AttributeError: 'NoneType' object has no attribute 'name'`.

Fix:

- Restored the database schema diagnostic implementation so `_database_diagnostic()` always returns a `Diagnostic`.
- Doctor now returns clean unknown JSON/text when an outer database access error is raised.

Regression tests:

- `test_database_diagnostic_returns_schema_status`
- `test_database_diagnostic_handles_unparsed_config`
